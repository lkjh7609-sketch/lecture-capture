오늘 수업 정리. 인자: `$ARGUMENTS`
- 첫 인자 = 입력 노트 파일(프로젝트 루트 기준). 
- DAY 번호가 없으면 파일명에서 추출(`SAP CODE DAY2.txt` → 2).
- 날짜가 없으면 오늘 날짜.
- 사용자가 메시지에 추가 메모를 붙였으면, 그 내용을 문서 맨 앞 절로 넣는다.

**Python 실행 규칙**: 아래의 `python3 _template/…py` 명령은 환경변수 `LC_PY`가 있으면(수업캡처 설치판 노트북, Python 없음) `"$LC_PY" _template/…py …`로 같은 인자를 넘겨 실행한다. 없으면 `python3`(Windows는 `python`).

## 0. 먼저 읽기
- 입력 노트 전체.
- `_template/html_reference.html`: HTML 디자인 기준. 구조, CSS, JS를 그대로 재사용한다.
- `_template/paper_reference.html`: PDF 디자인 기준. CSS, 표지, 목차 JS, `@page` 설정을 그대로 재사용한다.
- 이전 회차 원본 `_template/days/day*.html`은 목차와 제목만 훑는다. 이어지는 개념에 "DAY n 참고"로 연결하기 위해서다.

## 0-1. 입력이 `캡처/YYYY-MM-DD/timeline.md`일 때 (수업캡처 앱이 만든 파일)
- "화면 내용(캡처에서 옮김)" 블록: 수업 중에 캡처를 글로 미리 옮겨 둔 것이다. 이 글을 화면 원본으로 쓴다. 이미지는 그림·다이어그램 배치를 봐야 할 때나 내용이 이상할 때만 `(원본 이미지: …)` 경로로 연다.
- 이미지 줄(`![](shots/…png)`, timeline.md 기준 상대경로)이 있는 블록(★, 미리 옮기지 못한 장)은 이미지를 **전부** Read로 직접 본다. 코드와 화면 글자는 이미지를 기준으로 옮긴다. "화면 텍스트(OCR)"는 보조 자료라서 틀릴 수 있다.
- "이미지 생략" 블록은 다음 캡처에 포함된 중간 단계이니 메모와 받아쓰기만 쓴다.
- 비슷한 화면이 이어지면(코드를 치는 중간 과정) 마지막 완성본을 싣는다. 단, 중간에 에러 화면이나 다른 시도가 있었으면 그 과정도 살린다.
- "같은 화면에 추가(펜 필기·코드)" 블록은 그 화면의 마지막 모습이다. 같은 슬라이드의 원래 내용에 더해 **새로 생긴 부분**을 찾는다. 강사가 펜으로 동그라미 친 곳, 화살표, 손글씨는 강조한 지점이니 해당 설명에 "강사 강조"로 반영한다. 손글씨 내용도 글로 옮긴다.
- 내 메모와 ★ 블록은 사용자가 직접 중요하다고 표시한 것이다. 빠뜨리지 말고 눈에 띄게 다룬다.
- "강사 설명(받아쓰기)"은 원본으로 취급한다(보충 표시 안 함). 같은 블록의 화면을 설명하는 말이니 그 화면과 묶어서 쓴다. 받아쓰기에서 틀린 용어나 API명은 화면 글자를 기준으로 바로잡는다. 잡담, 출석, 쉬는 시간 안내 같은 수업과 무관한 말은 뺀다.
- 수업과 관계없는 화면(디스코드 대기 화면, 바탕화면 등)은 무시한다.

## 1. 두 파일의 역할
- **HTML = 전체 기록.** 원본 내용을 하나도 빠짐없이 넣는다. 다만 한눈에 보이는 건 핵심이고, 세부는 접어 둔다(2절).
- **PDF = 핵심 노트.** 나중에 다시 볼 때 이것만 보면 되게 만든다. 기준은 **처음 배우는 사람이 PDF만 보고 문법을 따라 쓸 수 있는가**다. 결론만 적은 요약(겉핥기)은 안 된다. 분량은 보통 10~15쪽(3절).

## 1-1. 중요도 판단 (PDF에 넣을지, HTML에서 펼쳐 둘지)
다음 신호가 있는 내용이 핵심이다. 많이 겹칠수록 위에 둔다.
- 내가 표시한 것: ★ 캡처, 내 메모.
- 강사가 강조한 것: 펜 필기(동그라미·밑줄·화살표), 여러 번 반복한 설명, "중요/시험/꼭/자주 틀린다/실무에서" 같은 말.
- 실제로 난 에러와 해결법.
- 이후 회차에서 계속 쓰이는 기본 개념(이전 회차 목차와 비교해 판단).
다음은 핵심이 아니다: 환경 설정을 따라 하는 단계(결과만 한 줄), 같은 예제를 조금씩 바꿔 친 중간 과정, 잡담.
원본에 "주의"로 표시된 내용과 실습 문제(문제와 정답 코드)는 PDF에 반드시 넣는다(한두 줄로 줄여도 된다).

## 1-2. 구조 한눈에 보기 (HTML·PDF 둘 다 필수)
그날 배운 함수·양식(View/Controller/Model, 바인딩, 이벤트, 라우팅, OData 호출 등)을 실제로 써먹으려면 **무엇이 무엇을 부르고, 데이터가 어디서 어디로 가는지**를 알아야 한다. 그날 핵심 흐름을 1~3개 골라 아래 형식으로 만든다.
- **그림**: 인라인 SVG 흐름도. 박스 = 파일·객체·함수(파일명 함께), 화살표 = 데이터/이벤트/호출. 화살표마다 ① ② ③ 순서 번호와 짧은 라벨을 단다. 라벨에는 흐르는 것(값, 이벤트, 호출)과 실제 코드 조각(`press=".onSave"`, `setModel()`, `{/name}`)을 함께 쓴다. 박스는 6개 이하.
- **간단한 설명**: 그림 바로 아래 3~5줄. 처음 보는 사람도 바로 이해하게 쉬운 말로 쓴다. 생활 비유 하나로 끝까지 간다(예: View=식당 홀, Controller=주문 받는 점원, Model=주방 냉장고, 바인딩=메뉴판에 오늘 재료가 자동으로 적힘). 비유의 각 요소가 그림의 어느 박스인지 짝지어 준다. 전문 용어는 비유 다음에 괄호로만.
- **따라가 보기**: 실제 한 번의 동작(예: 버튼 클릭 → 화면 글자 바뀜)을 번호 순서대로 4~6줄로 따라간다. 줄마다 그림의 번호와 그 단계 코드 한 줄을 붙인다.
- **고치면 어디가 바뀌나**: "이걸 바꾸고 싶으면 → 이 파일의 이 부분" 2~3줄. 자주 하는 실수(연결이 끊기는 지점)를 하나 표시한다.
- 이전 회차 흐름에 이어지는 것이면 그 그림을 바탕으로 새로 생긴 박스·화살표만 강조색으로 표시한다("DAY n 그림에 추가된 부분").

## 1-3. 공통 규칙
- 오타나 틀린 이름(파일명, 메뉴명, API명)은 바로잡는다. 따로 표시하지 않는다.
- 원본에 없는 보충 설명은 HTML에서 "보충" 배지, PDF에서 "†"로 표시한다. PDF의 보충은 꼭 필요한 것만.
- 목차에 제목만 있고 본문이 없는 절은 HTML에서 채우고 보충 표시를 한다.
- ABAP 비교(사용자는 ABAP 선행 학습자): HTML은 개념마다, PDF는 끝의 대응표 하나로 모은다.
- HTML: 원본 코드는 그대로 싣고 줄마다 설명한다. 에러와 해결법은 별도 절로 둔다.

## 2. HTML: `페이지_SAP_UI5_{DD_MM_YYYY}.html` (루트)
- 파일명에 `:` 금지(Windows에서 쓸 수 없음).
- `html_reference.html`의 레이아웃과 컴포넌트를 그대로 쓴다.
- 색은 파란 강조색 하나와 회색만 쓴다. 이모지 금지.
- 페이지 오른쪽 최상단에 라이트/다크 토글을 단다(화면 고정 아님, 스크롤하면 같이 올라감). 기본은 라이트, 고른 모드는 브라우저에 기억된다. HTML을 다 만든 뒤 반드시 `python3 _template/add_theme_toggle.py "페이지_SAP_UI5_{DD_MM_YYYY}.html"`을 실행한다(이미 있으면 최신으로 교체됨). 다크 색은 reference의 `:root[data-theme="dark"]` 토큰 블록을 그대로 유지해야 바뀐다.
- 이 명령 밖에서 만드는 HTML(연습장 등)도 루트에 저장하면 같은 스크립트로 토글을 넣는다.
- 고정 목차에 스크롤 위치를 표시한다(scrollspy).
- 다이어그램과 인터랙션(탭, 아코디언, 단계 진행, 펼침 설명)을 적극 활용한다.
- "구조 한눈에 보기"(1-2)는 "오늘의 핵심" 바로 다음 절로 둔다. 접지 않는다. reference의 `.diagram`(박스 클릭 → 옆 패널에 설명)과 `.flow`(단계 진행) 컴포넌트를 그대로 쓴다. "따라가 보기"는 단계 버튼을 누를 때마다 해당 화살표가 강조되게 한다. SVG 색은 CSS 변수(라이트/다크 토큰)로 칠해서 다크 모드에서도 보이게 한다.
- 맨 위에 "오늘의 핵심" 상자(3~5줄)를 둔다. 각 절은 처음에 핵심(정의·최소 코드·함정)만 보이고, 줄별 코드 설명·중간 과정·받아쓰기 원문·ABAP 비교 같은 세부는 접힌 상태("자세히")로 둔다. 1-1의 핵심 신호가 있는 내용은 "중요" 표시를 단다.
- 코드는 하이라이트하고 복사 버튼을 단다. 바인딩 표현에는 밑줄을 친다.
- 끝에 자가 점검 퀴즈를 둔다.
- 단일 파일로, 외부 의존 없이 만든다. 인쇄할 때 내용이 숨지 않아야 한다(print CSS 유지).
- 글꼴 스택은 reference 그대로 쓴다(Mac과 Windows 대체 글꼴이 모두 들어 있음).

## 3. PDF: `강의노트_SAP_UI5_{DD_MM_YYYY}.pdf` (루트)
- 소스 HTML은 `_template/days/day{n}.html`에 만든다. `paper_reference.html`을 복사한 뒤 본문만 교체한다.
- 바꿀 곳:
  - `<title>`
  - `@page` 머리글: `@top-left`를 "SAPUI5 실습 정리 · Day {n}"으로, `@top-right`를 날짜로.
  - 표지: kicker `STUDY NOTE · DAY {n}`, meta 날짜, 초록, 키워드.
- 표지 `<div class="sub">…</div>`(과정명과 이름)는 `paper_reference.html`에 적힌 값을 그대로 쓴다. 바꾸지 않는다.
- 제목 태그는 반드시 `<h2 id="sN"><span class="n">N.</span>제목</h2>` 형식으로 쓴다(h3도 같은 형식). 형식이 다르면 목차 쪽번호가 매핑되지 않는다.
- 그림, 표, 코드에 번호를 붙인다(그림 n / 표 n / 코드 n). 표 머리와 파일명 칸은 줄바꿈하지 않는다(`td.nw`).
- **분량: 보통 10~15쪽.** 줄여야 하면 문법 틀·예제가 아니라 중간 과정, 같은 내용의 두 번째 예제, 긴 배경 설명부터 뺀다. 구성:
  1. 오늘의 핵심 3~5줄 (초록 자리에)
  2. 구조 한눈에 보기(1-2): 흐름 하나에 한 쪽, 최대 2쪽. 그림(번호 붙은 그림 n) + 간단한 설명 + 따라가 보기. 인터랙션 없이 정적 SVG로, 글꼴은 번들 글꼴만.
  3. 개념 절: 그날 나온 문법·함수·양식은 **하나도 빼지 않고** 아래 순서로 쓴다.
     - **한 줄 정의**: 쉬운 말로 무엇인지.
     - **쓰는 법**: 문법 틀 코드(예: `if (조건) { } else if (조건) { } else { }`, `switch (변수) { case 값: …; break; default: … }`, `for (초기화; 조건; 증감) { }`). 자리마다 무엇이 들어가는지 주석.
     - **예제와 결과**: 수업 예제를 그대로 쓰고 `// 출력: …`으로 결과를 적는다.
     - **함정**: 원본의 "주의", 실제로 난 에러.
     - 틀과 예제는 `.two`로 나란히 놓아 공간을 아낀다.
  4. 에러와 해결 (표 하나: 증상 / 원인 / 해결)
  5. 부록: ABAP 대응표, 셀프 체크 5문항(답은 아래에 짧게). 용어 정리는 PDF에 넣지 않는다(HTML에 있음).
  6. 마지막 부록 "HTML에만 있는 내용": PDF에서 뺀 원본 항목을 하나도 빠짐없이 "항목 → HTML n절" 한 줄씩 적는다. 빠진 것 없이 원본 전체가 어딘가에 있다는 걸 이 목록으로 보장한다.
- 긴 줄별 코드 해설, 따라 하기 단계, 중간 과정, 긴 배경 설명은 PDF에 넣지 않는다. 필요하면 "자세한 내용: HTML n절" 한 줄로 연결한다.
- 마지막 `<script>`(목차 생성 JS)는 유지한다. build.py가 그 앞에 `window.__PAGES`를 넣는다.
- 글꼴은 `_template/fonts/`의 Noto Serif KR, Noto Sans KR, JetBrains Mono만 쓴다(`@font-face`는 reference에 있음). 시스템 글꼴 이름(Apple…, Malgun…)은 쓰지 않는다. 그래야 Mac과 Windows 결과가 같다.
- 특수문자는 번들 글꼴에 있는 것만 쓴다(예: `▾` 대신 `▼`).
- 빌드: `python3 _template/build.py _template/days/day{n}.html "강의노트_SAP_UI5_{DD_MM_YYYY}.pdf"`
  - Windows에서는 `python3` 대신 `python`. 모듈이 없다고 나오면 `pip install pymupdf`.
  - 출력의 `missing []`이 비어 있어야 한다.

## 4. 검증 (필수)
- `_template/.build/sheet*.png`를 전부 본다. 의심 가는 쪽은 `_template/.build/png/pNN.png`로 확대해서 본다.
- PDF를 원본 목차와 대조해서, 원본의 모든 소절이 PDF 본문이나 "HTML에만 있는 내용" 목록 중 한 곳에 있는지 확인한다.
- 확인할 것: 잘린 내용, 코드 줄바꿈 깨짐, 빈 쪽, 고아 제목, 목차 쪽번호, 흐름도 글자 겹침·화살표 어긋남, **문법마다 쓰는 법 틀과 예제가 있는지**, 코드에서 `===` `!==` `<!--` `=>` 같은 기호가 합자로 바뀌지 않았는지.
- HTML은 Chrome(없으면 Edge) headless 스크린샷으로 첫 화면과 다크 모드를 확인한다. 오른쪽 위 토글이 보이는지, 다크로 바꿨을 때 글자가 잘 읽히는지 본다.
- 문제가 있으면 고치고 다시 빌드한다.

## 5. 바탕화면에 복사
- 원본은 루트에 둔 채로, 완성된 HTML과 PDF를 바탕화면의 `자료` 폴더에 복사한다.
- 바탕화면 경로는 PowerShell `[Environment]::GetFolderPath('Desktop')`로 구한다(OneDrive로 옮겨진 바탕화면도 찾음). `자료` 폴더가 없으면 만든다.
- 같은 이름의 파일이 있으면 덮어쓴다(복사본이므로).
